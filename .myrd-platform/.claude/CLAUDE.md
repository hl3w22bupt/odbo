# 项目规范

执行任务时必须严格遵守以下规范。

## TypeScript 编码规范

### 类型定义
- 使用 interface 定义对象类型
- 避免使用 any，尽量使用精确的类型
- 使用联合类型代替枚举

### 命名规范
- 类名：PascalCase
- 函数名：camelCase
- 常量：UPPER_SNAKE_CASE
- 接口名：PascalCase（不加 I 前缀）

---

## Git 提交规范

### Commit Message 格式
```
<type>(<scope>): <subject>

<body>
```

### Type 类型
- feat: 新功能
- fix: 修复 bug
- docs: 文档更新
- style: 代码格式调整
- refactor: 重构
- test: 测试相关
- chore: 构建/工具链更新

---

## React 组件规范

### 文件结构
- 每个组件单独一个文件
- 组件名与文件名一致（PascalCase）
- 使用函数组件 + Hooks

### Props 处理
- 使用 TypeScript 定义 Props 类型
- 默认参数使用 ES6 默认值
- 避免过度解构

### 性能优化
- 使用 useMemo 和 useCallback 避免不必要的重渲染
- 使用 React.memo 包裹纯展示组件

# Agent 防卡死纪律：复杂编辑任务必须分解与增量输出

## 背景

Agent 运行环境设有「无输出超时」保护机制：当 Agent 连续较长时间（常见阈值为 180 秒 / 3 分钟）未产生任何文本输出时，系统判定 Agent 卡死并自动终止该次执行。一旦终止，Agent 在该次执行中已完成但尚未持久化的工作（如未落盘的文件编辑）将全部丢失，用户必须重新发起任务。

实际案例：一次前端重构任务中，Agent 高效完成了代码定位、并行文件读取、结构分析、类型确认和方案设计等全部前期工作。进入实际编辑阶段后，Agent 尝试在单次输出中同时完成三个子变更（双栏布局拆分、RunRow 子组件提取、死代码移除），连续 180 秒无任何输出，被系统终止。全部工作丢失。

此问题与「Git / Shell 命令阻塞型卡死」（由外部命令等待交互输入导致）属于不同故障模式：前者发生在**代码生成阶段**，根因是 Agent 试图一次性产出过大编辑内容而长时间无输出；后者发生在**命令执行阶段**。本规范专门针对前者。

## 适用对象

所有由平台调度执行的 Agent，包括但不限于 Express Agent、工作流节点 Agent 等所有类型。尤其适用于涉及多文件协调修改、大段代码生成或重构的编码任务。

## 具体要求

### 要求 1：任务分解（强制）

在开始实现任何代码编辑之前，必须先评估任务复杂度。如果任务包含以下**任一**特征，必须将其分解为有序的、可独立完成的子步骤：

- 涉及 2 个以上文件的协调修改
- 单次编辑预期会产生超过 50 行的新增或替换代码
- 包含多个独立的逻辑变更（如「重构布局 + 提取组件 + 删除死代码」是三个独立变更）

**分解方式**：在开始编辑前，先输出简短的有序子步骤清单（示例：「我将分 3 步完成：①提取 RunRow 组件到新文件 → ②修改主布局为双栏 → ③清理废弃的筛选开关」），然后逐个执行。

### 要求 2：增量输出（强制）

执行过程中必须保持输出节奏，确保任意两次文本输出之间的间隔不超过 60 秒。具体做法：

- 每完成一个子步骤后，立即输出该步骤的完成摘要（1-2 句话即可，如「步骤 1 完成：RunRow 组件已创建于 src/components/RunRow.tsx」）
- 如果某个编辑操作本身可能需要较长时间（如生成大段代码），在开始前先输出意图声明（如「正在生成双栏布局代码，预计涉及 ~40 行修改…」）
- 如果发现当前步骤比预期复杂，先输出当前进展和调整后的下一步计划，再继续执行

### 要求 3：单次编辑体量控制（强制）

避免在单次操作中生成过大的编辑内容：

- 单个文件的编辑尽量控制在 100 行变更以内；如果必须更大，先完成核心逻辑部分并输出，再补充其余部分
- 涉及多文件时，逐文件编辑、逐文件输出确认，而非一次性输出所有文件的修改
- 对于「提取组件 / 提取函数」类操作，**先创建新文件并输出**，再修改引用方文件——切勿将「新建 + 引用修改」合并为一次输出

### 要求 4：关键节点进度通报（强制）

对于预计执行时间超过 2 分钟的任务，必须在以下关键节点输出进度通报：

- 前期分析完成后（如「已完成代码结构分析，共识别 3 处需修改，进入实现阶段」）
- 每个子步骤完成后
- 遇到意外情况时（如「发现 RunRow 需要额外的 props 类型定义，正在补充…」）

## 违反后果

- Agent 连续无输出达到超时阈值 → 系统自动终止执行
- 该次执行中所有未持久化的工作（文件编辑、代码生成）全部丢失
- 用户必须重新发起任务，造成时间和计算资源双重浪费
- 任务交付延迟，用户信任度下降

## 正确示例

❌ **错误做法**（来自实际失败案例）：

> Agent 读取多个文件、完成全部分析后，尝试在单次输出中完成「双栏布局拆分 + RunRow 组件提取 + 死代码移除」三个变更。连续 180 秒无输出 → 被终止。全部工作丢失。

✅ **正确做法**：

```
[分析完成后输出]
分析完成。该区块当前为单栏 IIFE，涉及 738-836 行。计划分 3 步重构：
  ① 提取 RunRow 组件到新文件
  ② 修改主布局为 lg:grid-cols-2 双栏
  ③ 移除废弃的筛选开关
开始执行步骤 ①。

[创建 RunRow.tsx 后输出]
步骤 ① 完成：RunRow 组件已创建。开始步骤 ②。

[修改主布局后输出]
步骤 ② 完成：双栏布局已应用。开始步骤 ③。

[清理完成后输出]
步骤 ③ 完成：废弃筛选开关已移除。全部重构完成，代码可编译。
```

每步之间均有输出，全程无超过 60 秒的静默区间，不会触发超时终止。

# 长任务执行韧性规范

## 背景
长耗时的 agent 任务可能因 worker 生命周期事件（SIGTERM/SIGINT 等信号）被中断，或因长时间无进展被判定为僵尸轨迹而清理失败。此类失败在本平台多轮反复出现、代价高（结果丢失、任务重做、排障与重试成本），且已同时影响后台分析类与记忆蒸馏类任务。

## 适用对象
所有设计或实现长耗时任务（预计执行时长接近或可能超过平台默认执行时限）的 agent 与 workflow 节点。

## 要求
1. 心跳上报：长任务必须在执行期间周期性上报心跳/进度；上报周期应显著短于系统执行时限（建议不超过时限的 1/3）。
2. 可恢复进度：任务必须具备断点/checkpoint 能力，将已完成阶段持久化；中断后能在不重头执行的前提下恢复。
3. 有界执行：任务必须显式设置内部超时与取消响应；收到取消请求时应尽快退出并完成状态同步，不得无限阻塞。
4. 语义区分：必须区分「取消」与「失败」——被取消的轨迹不应被当作失败重试，也不得污染失败统计。
5. 外部中断处置：收到 worker 生命周期终止信号时，应尽力保存进度与部分结果后再退出，避免输出完全丢失。
6. 禁止盲目重试：对基础设施层中断，不得以与原来完全相同的配置无限重试；应先评估是否具备可恢复进度，再决定重放策略。

## 违反后果
- 轨迹频繁以「中断/挂起/僵尸」形式失败，产出丢失且无法恢复。
- 盲目重试放大资源消耗与平台负载，影响同批其它任务。
- 取消被误判为失败，导致错误告警与统计失真。

## 示例
- 错误示例：一个预计执行 40 分钟的任务，无心跳、无 checkpoint，而平台执行时限为 30 分钟 → 必然被判定为僵尸轨迹，失败后无任何中间结果可恢复，只能整体重跑。
- 正确示例：任务每 5 分钟上报一次进度，每完成一个阶段写入 checkpoint；收到 SIGTERM 时保存当前阶段并干净退出；重启后从最后一个 checkpoint 恢复，重放代价被压缩到最小。

## 说明
本规范为通用约束，适用于任何采用「worker 执行池 + 轨迹超时清理」模型的 agent 平台。

# 内容产出类 Agent 产物持久化纪律

## 背景
多条内容营销工作流执行中，agent 以退出码 0 结束却未产生任何 git commit：产物仅存在于对话输出，工作区无落盘文件，导致工作流判定失败、交付物丢失。根因包括：(1) agent 误以为会话只有只读工具（read/grep）而放弃写入；(2) agent 进入 Plan Mode 等待审批后停滞；(3) 缺少「产物必须持久化」的显式纪律。该规律跨多个运行反复出现，属于必须遵守的执行红线。

## 适用对象
所有承担内容/文档/代码产出的执行型 agent（软文撰写、营销稿、报告、代码生成、后台蒸馏/分析等），以及其所在工作流节点的提示词设计。

## 具体要求
1. 产物落盘：任何交付物必须以文件形式写入当前工作区（Markdown/代码文件），不得仅以对话文本返回。
2. 版本控制：完成落盘后必须执行 git add 与 git commit 提交，退出前确认 git log 中存在本轮 commit。
3. 工具边界核实：执行前确认自身具备写文件与 git 能力；若发现疑似只读限制，先查阅装配的技能/知识确认真实工具清单，而非直接放弃写入。
4. 禁止停滞：不得停留在 Plan Mode / 等待审批而不推进；如确需澄清，先完成可确定的产出并 commit，再列出待确认项。
5. 分段持久化：长文档建议分段写入多个文件，降低中断丢稿风险。

## 违反后果
- 工作流节点被标记为失败（即使退出码为 0）；
- 交付物无法回收/检索，需人工重新执行；
- 增加后续记忆蒸馏与排查成本。

## 示例
- 正确：产出 AIDA 母稿 → 写入 aida-01..04.md → git add + commit「公众号 AIDA 母稿四段」→ 退出。
- 错误：产出全文后仅粘贴在对话中，未写文件未 commit，退出码 0 → 判定失败。

# Workflow Agent 节点执行纪律规范（反挂起）

## 背景
本平台上多个 workflow agent 节点（典型如 create-pr、frontend）在长时间操作（git push、gh pr create、依赖安装、前端构建等）中表现为 status=running 且长时间无任何输出、无错误信息。单次分析即发现 7 条失败轨迹跨 channel / workflow / express_lane 三种执行类型，均无 error、无 outputPreview。根因之一在于 agent 节点提示词只约束了「不得进入 plan mode」，缺少对长时间运行命令的执行纪律约束，导致 agent 在凭据提示、网络阻塞、长构建上无限等待，轨迹永远无法 finalize。

## 适用对象
- 所有在 本平台上创建 / 编辑 workflow agent 节点的编排者
- 所有承载 agent 任务的系统提示词 / workflow 节点提示词
- express_lane、channel agent、exploration、onboarding 等所有执行类型

## 具体要求
1. **进度可见性**：每个完成的步骤 / 每个产出的文件后，必须向输出流写入一条进度信息；禁止静默运行超过 10 秒。
2. **超时中止**：任何单个命令超过 60 秒仍无新输出，或处于等待交互输入状态时，必须自动中止该命令（SIGTERM → 10 秒后 SIGKILL），并报告超时原因。
3. **重试上限**：单个操作最多重试 2 次；每次重试前必须输出失败原因；超过上限必须以显式失败结束。
4. **非交互化**：所有可能进入交互提示的命令必须使用非交互 flag，例如 `gh pr create --non-interactive`、`git -c core.askpass= push`、`npm install --no-fund --no-audit`，严禁依赖人工输入（避免凭据提示死锁）。
5. **禁止请求人工确认**：不得以任何形式暂停等待人类确认 / 输入。
6. **显式失败**：失败必须以非零退出码 + 明确的错误消息结束，使轨迹可被 finalizeAgentTrajectory 正确落为 failed，而非停留在 running。

## 违反后果
- 轨迹永久停留 running，无输出无错误，无法被进化分析利用，也占用了 Worker 进程与工作区资源；
- 多次发生将导致轨迹表被孤儿记录污染，平台可观测性下降。

## 示例（符合规范的节点提示词片段）
```
执行约束（必须遵守）：
- 每完成一个文件修改或一个命令，立即输出 "[done] <简述>" 进度。
- 每个命令必须加超时：超时 60s 无输出即终止；git/gh 必须带非交互 flag。
- 单操作最多重试 2 次，重试前输出原因。
- 失败时以 exit 1 结束并输出错误摘要，绝不静默退出 0。
- 全程不得请求人工确认。
```

# Agent 防卡死纪律规范（复杂编辑与长时间命令）

## 背景
运行轨迹显示，执行编码/改造任务的 agent 会长时间（≥180s）不产生任何输出，被运行时看门狗判定为"疑似卡死"并自动终止，导致已完成的修改全部丢失、任务整体失败。已知两种典型失效模式：
1. **复杂编辑静默**：一次性执行跨多文件的大型编辑（如同步进行组件抽取 + 布局拆分 + 死代码清理），期间无任何中间输出；
2. **长时间命令静默**：执行 `prisma generate`、`npm install`、全量编译等可能长时间无返回的命令，或环境未就绪（如 Prisma 客户端未生成导致大量既有编译错误）时，agent 在命令执行/环境处置阶段无输出地等待直至被终止。

## 适用对象
所有执行自动化开发/改造任务、可能产生长时间无输出窗口的 agent（含定时调度 agent 与工作流节点内 agent）。

## 强制要求

### 1. 任务分解
- 涉及 ≥2 个文件、≥50 行新代码、或包含多个相互独立逻辑改动的任务，必须先输出有序的子步骤计划，再逐步实施。
- 多文件改动按文件逐个处理，禁止在一个无输出窗口内连续改动多个文件。

### 2. 增量输出
- 任意两次文本输出间隔不得超过 60 秒。
- 每个工具调用完成后、每次进入可能耗时的阶段前，必须输出一行简短进度说明。

### 3. 单次编辑量控制
- 单次编辑建议控制在约 100 行以内；大段代码拆为多次顺序编辑。

### 4. 长时间命令可观察性
- 执行可能静默超过 60 秒的命令（`prisma generate`、依赖安装、全量构建、git 大操作等）前，先输出"将执行 XX 命令，可能需要一段时间"的说明。
- 优先使用带输出/进度/verbose 标志的调用方式；无法流式输出时，将命令拆分为更小步骤，避免单条命令长时间无返回。
- 命令被看门狗拦截或长时间无返回时，不要原地等待，立即改为分块执行，或输出结构化错误与替代路径后退出。

### 5. 环境预检与基线编译
- 动手前先确认环境就绪：依赖是否安装、代码生成器是否已执行（如 Prisma 的 `npx prisma generate`）。
- 对已有编译错误的项目，先建立"基线编译"结果，明确既有错误集合，再开始改动；只处理与自身改动相关的新错误，避免被大量既有错误困住而无输出。

### 6. 显式失败上报
- 禁止静默挂起：能力不足、工具缺失、环境阻塞时，必须在超时前输出结构化错误摘要（已尝试路径 + 替代路径），随后以非零退出码结束。
- 禁止在等待人工确认或等待未知网络/命令返回时空转。

## 违反后果
- 被运行时看门狗自动终止（典型阈值：连续 180s 无输出）；
- 当前会话所有未保存的修改丢失；
- 浪费计算资源、任务交付延迟、用户信任受损。

## 示例
- **错误做法 A**：一次任务内同时做三个互不相关的改动，期间不输出进度，180s 后被打断，工作全部丢失。
- **错误做法 B**：编译报大量 `@prisma/client` 缺失错误后，不先执行 `prisma generate` 修复环境，也不输出处置说明，在排查中静默直至被终止。
- **正确做法**：
  1. 先输出任务分解计划与环境检查结果（依赖/生成器就绪情况）；
  2. 跑基线编译并记录既有错误数；
  3. 逐个文件完成编辑，每完成一个子步骤输出一句进度；
  4. 运行 `prisma generate` 前输出"正在重新生成 Prisma 客户端"；
  5. 保持每步间隔 <60s，最后输出变更清单、编译结果与新旧错误对比。

# 规范：Agent 执行轨迹（agentExecutionTrajectory）有界生命周期与僵死自愈

## 背景
平台每次 Agent 执行（channel 频道消息 / express_lane 直通车 / workflow 内 agent 节点 / exploration / onboarding / secretary）都会写入一条 agentExecutionTrajectory 轨迹，status 初始为 running。轨迹仅在底层 pipeline 正常结束（final 事件或流自然结束）时被置为 completed，在 catch 异常时被置为 failed。轨迹是进化分析的数据底座，也是排查运行问题的主要依据。

## 现象
生产观测到多条轨迹长期停留在 status='running'，且 error=NULL、outputPreview=NULL（无输出、无错误）。这类记录既不结束也不报错，无法区分「正在正常执行」「子进程卡死」「Worker 重启后失联」三种状态，导致：前端永远显示执行中；进化分析持续拿到空样本；残留的 claude 子进程与 worktree 泄漏资源。

## 根因
1. 轨迹完结只发生在进程内 pipeline 的正常/异常返回路径；进程级中断（Worker 重启、OOM、宿主机重启）不经过这些路径，轨迹被永久孤儿化。
2. Worker 启动自愈已覆盖 workflowRun（→paused）、expressLaneRun（→failed）、channel_messages streaming 占位消息、goal 执行与 agent busy 状态，但**不覆盖 agentExecutionTrajectory 本身**（src/index.ts 启动自愈清单中无该表）。
3. 自愈均为启动时一次性执行，运行期没有周期性僵死检测。

## 适用对象
所有写入 agentExecutionTrajectory 的执行环节：channel、express_lane、workflow 节点、exploration、onboarding、secretary。

## 具体要求
1. 【有界生命周期】任何一条轨迹从创建到终结必须有硬上界（建议 30 分钟，与 express-lane 轮询超时一致）。到达上界仍未 finalize 的，应被标记为 failed，error 注明「执行超时」。
2. 【全路径完结】轨迹必须在所有路径完结：正常 final、流自然结束、异常 catch、Abort、Worker 重启恢复。任何新增执行环节（新 agentType）必须同时提供对应的完结路径与自愈覆盖。
3. 【僵死自愈】对 agentExecutionTrajectory 提供僵死回收：启动时 + 周期任务（如每小时），将 created_at 超过阈值仍为 running 的轨迹标记为 failed，error 注明「执行中断（Worker 重启/超时）」，并尽力保留已产生的 outputPreview。
4. 【可观测性】运行中必须持续产出中间输出（进度文本 / segments），避免「运行中但零输出」；无任何输出的运行时长超过 10 分钟即应触发回收或告警。
5. 【资源联动】轨迹被判僵死后应联动回收：残留 claude 子进程（按 sessionId/worktree 定位）、worktree 目录、streaming 占位消息。

## 违反后果
- 轨迹永久 running：前端「执行中」永不结束，用户无法判断真实状态、无法放心重试。
- 进化分析持续拿到 status=running 的空样本，无法学习且误判为大量失败。
- 僵尸 claude 子进程与 worktree 累积，消耗磁盘与 CPU。

## 示例
- 错误示例：channel 轨迹运行 3 小时仍为 running，error=NULL，outputPreview=NULL，前端一直显示「生成中…」，用户无法取消或重试。
- 正确示例：同一轨迹运行 20 分钟仍无输出后被回收为 failed，error='执行中断（无输出超时）'，关联的 ExpressLaneRun 联动标记 failed，对应 worktree 被清理，用户可一键重试。
